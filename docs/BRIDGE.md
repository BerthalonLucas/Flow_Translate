# React ↔ Rust bridge, version 2 (FlowTranslate 0.4.0)

> La DA Îlot ([docs/DA-PLAN.md](DA-PLAN.md)) étend ce contrat sur la branche da-ilot ; les sections concernées sont mises à jour lot par lot.

## Actions, instructions and the language in the prompt (0.3.0 → 0.4.0)

The current `Settings` replaces the legacy `shortcut` field with `actions: ActionDefinition[]`, `shortcutBindings: ShortcutBinding[]`, and `defaultActionId: string`. `ActionDefinition` is `{id, name, promptTemplate}`; `ShortcutBinding` is `{id, shortcut, actionId, outputMode: 'display'|'replace', enabled}`. `src/types.ts` is authoritative for the current contract.

Each native capture includes `execution: {actionId, actionName, outputMode, mode}` (no `targetLanguage` since 0.4.0: the language lives in the instruction). Rust snapshots the corresponding action, prompt and profiles at capture time; the frontend sends `actionId` in `TranslationRequest`, never a prompt. Initial mode and action must match the capture. A comparison/retry may change the profile, but cannot perform another automatic replacement.

`result-delivery` emits `{requestId, status: 'applied'|'fallback', confirmed: boolean, message}` (0.4.0). Stale IDs and closed overlays ignore it. As soon as a « replace » request completes, Rust claims delivery once, revalidates the native target and pastes under the session lock (`capture::paste`, Ctrl+V into the original selection, clipboard restored); `confirmed` says whether the field was read back with the result (bonus proof, never a condition). Before it, the frontend keeps the pill alone; on `applied` the pill shows a check for 900 ms then calls `dismiss_overlay`; on `fallback` the glass opens with the result, the message and Copier; without any report three seconds after `done` the frontend treats it as `fallback`. Cancelling even a completed request revokes a pending delivery. Failure leaves the result in the bubble. `capture-target` cannot reactivate replacement after a successful automatic write.

Settings persist through a serialized save queue in React and a mutex in Rust. Registration and persistence errors roll back newly registered shortcuts. Existing API keys remain DPAPI-encrypted. Legacy settings retain their shortcut and profiles; newly reserved legacy shortcuts are disabled, not discarded. Since 0.4.0 a prompt is the instruction alone (1 to 8,000 Unicode characters, no NUL, no variable): Rust sends it as the `system` message and the captured text as the `user` message, so the text is never substituted into the instruction. 0.3.0 templates are migrated on load: `{{targetLanguage}}` becomes `French`/`English` from the former « Langue cible » setting, `{{text}}` and its line are dropped; `defaultActionId` falls back to the first action when its id is gone (`translate` → `translate-fr`).

The settings window is now user-resizable with a dedicated scroll viewport. `resize_settings` was removed; corner dragging calls Tauri `startResizeDragging('SouthEast')`, permitted only for the settings window. Native minimum dimensions are 460 × 420 logical pixels.

Rust structs serialize camelCase. Rust command names are snake_case; invoke arguments use camelCase. Strings returned as errors must be user-readable French and contain no payload or credentials. Since lot 10 of docs/DA-PLAN.md every failure that reaches the frontend as data also carries a code (`ErrorCode`, see « Îlot: error codes »), translated by the frontend into English or French; the French string stays for the v4 journey. The absence of content and secrets in errors remains the rule.

## Îlot: the menu, its keyboard and its focus (uiVersion `ilot`, lot 3)

Only with the hidden `uiVersion: 'ilot'`; in `v4` nothing below changes the old path.

- **Menu capture.** A press of an enabled binding with `kind: 'menu'` captures as before but carries `menu: {lastActionId: string|null}` and **no** `execution`. Rust keeps, for that capture only, a snapshot of the settings at the press and the source window; the frontend shows the menu and does not call `translate` yet. A press while one of our windows (overlay, halo, settings) is in front never takes it as the source: nothing is captured.
- **Choice.** `choose_action({captureId, actionId, instruction?}) -> ExecutionInfo`, once per menu capture (a second call, a stale id, a closed or closing overlay, a direct capture: French error). `actionId` is a saved action of the snapshot, or `'instruction'` with `instruction` (1 to 1,000 Unicode characters after trim, no NUL): Rust builds an ephemeral action « Instruction » whose system prompt is a short rewrite template (follow the user's instruction, keep language, meaning, names and facts unless told otherwise) + the instruction + the usual output rules. The output mode is always `replace`. Rust then sets `capture.execution`, closes the menu scope, makes the overlay non-activatable and, if the overlay holds the foreground, gives it back to the source at once. The frontend then calls `translate` exactly as for a direct capture, with `actionId` = the returned `execution.actionId` (`'instruction'` for a free instruction: the instruction itself never travels again, it stays frozen in Rust). `translate` on a menu capture before its choice is refused (« Choisissez d’abord une action dans le menu. »). The instruction is never logged, stored or saved as an action.
- **Keyboard.** `focus_overlay() -> boolean`: the menu calls it once when it appears. Rust waits (off the main thread, ≤ 900 ms) until the overlay is shown, activates it and answers `true` only if the overlay really holds the foreground afterwards (polled ≤ 40 ms; Windows may refuse the switch). With `true` the WebView owns the keyboard: Enter, letters, Tab, arrows, digits, Space and a real `<input>` for the free instruction (AZERTY, dead keys, IME), Escape included (the native hook passes every key while the menu is open and the overlay in front). With `false` the source keeps the foreground and the low-level hook forwards, only while the menu is open and the source in front, the menu keys as `menu-key` and swallows them: Enter, Escape, Tab (with `shiftKey`), arrows, the physical digits 1–6 (row or keypad, so AZERTY needs no Shift), and letters without any modifier read through the source's active layout (ToUnicodeEx, no keyboard state change). Never a chord (Ctrl, Alt or Win held), never Space: no free instruction in that mode. Known limit (measured 2026-09-24): Win11 Notepad gives its keyboard focus to its XAML menu bar on any Alt release it receives (masking keys such as `vkE8` do not prevent it); with the overlay in front the release never reaches it, but in the fallback it does, so the revalidation refuses the paste (nothing is written) and Escape leaves Notepad's focus on its menu bar. The 0.4 direct path meets the same release (the overlay never takes the foreground there): a direct « replace » in that Notepad is refused the same way, with a plain direct binding as with a `menu` binding under `v4`.
- **Escape.** In the focused menu the WebView handles Escape (the Îlot of lot 7 first goes back a level, from the grid or the field to its compact state, then closes; forwarded as `menu-key`, the same table applies). `dismiss_overlay` gives the foreground back to the source when the overlay holds it, then closes as before; nothing is pasted.
- **Keys typed during the capture** (review of da-ilot, n°4 and n°7). A `menu` binding opens the menu's scope at its press, before the capture is taken (a synthetic copy first waits for the chord's release), unless one of our windows is in front. The menu keys typed in the source meanwhile never reach it: Rust holds them and emits them as `menu-key`, in order, right after the `capture` event, with the new capture id. Without a capture (nothing selected, an error) they are dropped, never replayed in the source, and the scope goes back to what is still shown: the previous menu's, the glass's Escape scope, or none.
- **Leaving the menu** (review of da-ilot, n°2 and n°6). Once the overlay has held the foreground for a menu (`focus_overlay` answered `true`, or the hook saw it in front), the hook never takes a key from the source again for that menu: the fallback only serves a menu whose activation was refused. If the user then goes back to the source (a click in his document) or to another application while the menu still waits, Rust closes it as `dismiss_overlay` would (scope closed, Îlot hidden, nothing pasted), within one 35 ms watcher tick. A menu whose selection the watcher drops (window moved or left, selection changed or collapsed) closes the same way instead of receiving `target-invalidated`, and `choose_action` refuses it (« La sélection a changé; le menu est fermé. »). A menu already chosen is never closed by these rules.
- **After the choice.** The overlay carries `WS_EX_NOACTIVATE` and `silent_frame_proc` answers `MA_NOACTIVATE` to `WM_MOUSEACTIVATE`, so a click on the pill (Undo later) never takes the focus from the source; the hit tester keeps the bit through its style rewrites. Lifted at the next capture. A direct `display` binding keeps the old behaviour.
- **Automatic paste.** Like `replace_result`: if one of our windows is in front, Rust reactivates the source and revalidates the target after that (`capture::paste(..., reactivate=true)`, `validate_target` after the reactivation, never before); if another application is in front, it refuses (« La fenêtre source a changé; remplacement refusé. ») and the result stays in the glass.
- **Test switch.** With `FLOWTRANSLATE_CDP_URL` set (WebView2 probe only), `FLOWTRANSLATE_REFUSE_FOCUS` makes `focus_overlay` answer `false` without activating, to exercise the fallback on a real desktop.
- **Frontend.** The Îlot of lot 7 (`src/menu/IlotStage.tsx`, rendered by `GlassSession` while a menu capture's form is pending) drives this contract since 2026-09-24; the provisional `NativeMenuProbe` is gone. `focus_overlay` is called once per menu capture, when its stage mounts, never for a capture already chosen (double press). `menu-key` events are kept by `useTranslation` for their menu capture until the Îlot shows, so a key forwarded before the first render is not lost; a forwarded key also means the source is in front (injected mode: no field, ✦ dimmed) until a later `focus_overlay` answer says otherwise. A choice calls `choose_action` once, the surface turns into the working pill at once, and a refused choice (French error, announced to assistive technologies) gives the menu back.

## Îlot: shortcut, bindings and triggering (lot 4)

- **Fresh install.** Five English actions, in the order of the grid, each with its letter, short name and Lucide icon: `correct` « Fix grammar » (F, Fix, SpellCheck), `translate` « Translate » (T, Translate, Languages: French → English, anything else → French, one action), `professionalize` « Make professional » (P, Pro, BriefcaseBusiness), `shorten` « Shorten » (S, Shorten, FoldVertical), `email` « Write email » (E, Email, Mail). `menuActionIds` = those five in that order, `defaultActionId` = `correct`, and exactly one binding: `{id:'menu', kind:'menu', shortcut:'Ctrl+Alt+Space', actionId:'correct', outputMode:'replace', enabled:true}`. `src/actionDefaults.ts` mirrors `actions.rs`. The free instruction is not a saved action.
- **Under `uiVersion: 'v4'`** a `menu` binding runs `defaultActionId` directly and replaces the selection (its own `actionId` and `outputMode` are ignored); everything else of the 0.4 path is unchanged.
- **Migration of a 0.4 file** (a file without `menuActionIds`, read once then rewritten): every action, id, name, instruction and binding is kept, nothing is renamed (`Ctrl+Alt+T → translate-fr` stays a direct binding). The default actions it lacks are added by id at the end (a 0.3 `translate` action keeps its name and instruction and takes the grid's place); each grid action gets its letter when free, else the first free letter of its name; actions outside the grid get none; `menuActionIds` = the default ids present; the menu binding on Ctrl+Alt+Space is added unless a binding (even disabled, any spelling) already uses that chord; `defaultActionId` and `uiVersion` are untouched (a 0.4 file has no `uiVersion`: it reads as the Rust default, `ilot` since jalon B; the browser preview and the e2e fixture keep `v4` by default until their tests are rewritten for the Îlot at lot 14). A file older than 0.4 (no `actions`) first gets the four 0.4 actions (`translate-fr`, `translate-en`, `correct`, `professionalize`) and its one shortcut on `translate-fr`, then the same migration.
- **Last action per application.** At a menu capture Rust reads the source window's executable name (`notepad.exe`, lowercase, never a path or a title) and sets `menu.lastActionId` to the saved action last chosen there, if it still exists (else `null`: the frontend falls back to `defaultActionId`). `choose_action` records a saved action (never a free instruction, never any text) in `menu-memory.json` next to `settings.json`: `{applications: [{process, actionId}]}`, most recent first, 64 applications at most, written through a temporary file then renamed. An unreadable file is an empty memory.
- **Double press.** A second press of the same `menu` binding less than 400 ms after the first (dated when the shortcut event arrives, before any capture work) never captures: while that menu waits, Rust emits `menu-repeat` `{captureId}` to the overlay; if the first capture is still being taken, the event follows as soon as it is stored; if the menu was already chosen or closed, nothing happens. `useTranslation` answers `menu-repeat` itself (so it holds before the menu renders): `choose_action` with `menu.lastActionId ?? defaultActionId`, then `translate` as for any choice. Presses are `MOD_NOREPEAT`: holding the chord does not repeat. The second press chooses while Ctrl+Alt are still held, so `choose_action` gives the foreground back to the source only once the modifiers are up (the overlay keeps it and receives the release, ≤ 1.5 s), and a paste that must reactivate the source waits for the release first: released over the source, Alt would move its focus to its menu bar (Win11 Notepad) and the revalidation would refuse the paste.
- **AltGr.** `shortcut_conflict({shortcut}) -> {altGr: boolean, character?: string}`: for a chord holding Ctrl and Alt on a key that types something (letters, digits, punctuation, Space), Rust asks `ToUnicodeEx` (no keyboard state change) what Ctrl+Alt (+Shift) + that key types on the layout of the foreground window's thread (the settings window while its recorder listens). French AZERTY: `Ctrl+Alt+E` → `{altGr: true, character: '€'}`; `Ctrl+Alt+Space` → `{altGr: false}` (a plain space is not a conflict); a dead key counts. The browser preview answers for French AZERTY. The recorder asks it for every enabled chord holding Ctrl and Alt and shows a warning under it (never a refusal; lot 13).
- **A chord another application holds.** `Ctrl+Alt+Space` may already be registered by another application (`RegisterHotKey` answers `ERROR_HOTKEY_ALREADY_REGISTERED`; measured on the development PC on 2026-09-24, where the chord brought another application to the front): FlowTranslate then cannot register it and reports it at startup like any refused shortcut, opening the settings. The real-window checks of lots 3–4 used `Ctrl+Alt+Shift+Space` in their test settings.

## Îlot: the Settings window (lot 13)

- **Direct links.** Every field an error may point to carries a stable `data-field`: `menuShortcut`, and `quality|fast` + `.endpoint|.apiKey|.model` (`quality.endpoint`…). `SettingsField` (`src/types.ts`) also accepts a bare `endpoint|apiKey|model`, meaning the default profile's (`settings.mode`). The window takes the field from its URL at opening (`?window=settings&field=…`) or from the event `settings-focus-field` `{field}` while open; it opens the Connection details if needed, scrolls to the field, focuses its control and makes it pulse 2.8 s (reduced motion: the same highlight, still). An unknown field is ignored. The frontend calls `open_settings({field})` (`bridge.openSettings(field)`); Rust shows and focuses the window, then emits `settings-focus-field` to it (lot 10, see « Îlot: error codes »).
- **Changes made elsewhere.** The window adopts a `settings-changed` whose content differs from its copy when nothing is pending there (no typing waiting for its 300 ms, no save in flight, no unsaved edit); otherwise its pending edit wins and is saved.
- **Refusals.** Rust's French refusals of a save that the window can meet (shortcut taken, duplicate, letters, grid) are shown in the interface language (`src/settings/messages.ts`) until the error codes of lot 10.

## Îlot: error codes (lot 10)

- **Where.** `code` (`ErrorCode`, snake_case) travels beside the French `message` wherever a failure reaches the frontend as data: `translation` `{kind: 'error', message, code}`, `result-delivery` `{status: 'fallback', message, code}`, `capture-notice` `{message, code}`, `target-invalidated` `{…, code: 'target_changed'}`, and `check_connection` → `{connected: false, message, code}`. The list is the frontend's (`src/result/errors.ts`): `unreachable`, `timeout`, `unauthorized`, `model_not_found`, `bad_endpoint`, `busy`, `length`, `stream_broken`, `paste_blocked`, `target_changed`, `not_editable`, `too_long`, `cancelled`, `server_error`, `no_selection`, `protected_field`, `keys_held`, `internal`; a code it does not know reads as `internal`. The v4 journey keeps reading `message`. A rejected command still answers a French string (the 0.4 contract, unchanged so v4 keeps its texts); in the Îlot's journey those rejections are the frontend's own races or mistakes (a stale capture, a second choice, an action that does not match its capture) and read as `internal`: every failure that asks something of the user arrives as one of the events above.
- **Server** (`inference.rs`). Nothing at the address (refused, unknown host, TLS, no connection within 5 s) → `unreachable`; a server that accepted then stayed silent past 120 s, before or during the stream → `timeout`. Statuses (`error::http_status`): 401 and 403 → `unauthorized`; 404 whose body mentions « model » (vLLM « The model … does not exist », OpenAI `model_not_found`, Ollama) → `model_not_found`; any other 404, and a 3xx (redirects are never followed: the address is wrong) → `bad_endpoint`; 429 and 503 → `busy`; any other status (400, 500, 502…) → `server_error`. An address the settings refuse (`validate_endpoint`) → `bad_endpoint`. The stream: `finish_reason: length` → `length` (never pasted); any other reason than `stop` → `server_error`, and the reason is no longer part of the message (it is the server's word); unreadable UTF-8 or JSON, an event cut in the middle, no `stop` or no `[DONE]`, a body cut short → `stream_broken`; a complete answer with nothing in it (a thinking block alone) → `server_error`. Cancelled, or overtaken by a newer request → `cancelled` (the pill just leaves). An HTTP client that cannot be built, a display that fails → `internal`. `check_connection` classifies the same way on `/v1/models`: any 404 there is `bad_endpoint`, an answer that is not a model list is `bad_endpoint`, a model the list lacks is `model_not_found`.
- **The server's body** only classifies (a retry without the extra sampling fields, a 404), inside `inference.rs`: never in a message, an event, a log or a test output.
- **Capture** (`capture-notice`). Nothing selected (no UIA selection, no copy) or the Settings window in front → `no_selection`; a password field, or a field UIA cannot tell apart → `protected_field`; over 6,000 characters → `too_long`; the source window changed during the capture → `target_changed`; the tray's « Revoir » with nothing recent → `no_selection`.
- **Paste** (`result-delivery` fallback). Another application in front, the field, the element or the selection changed (collapsed to the caret included) → `target_changed`; the watcher had already dropped the selection → `target_changed`; a capture that never had a writable selection (a console, a password field, a copy the user made himself, a replay) → `not_editable`; the shortcut's keys still held after 600 ms → `keys_held`; a NUL in the result, the clipboard busy, the chord blocked, a source that cannot be brought back to the front → `paste_blocked`.
- **Tests.** Every code is produced in the Rust tests by a fake OpenAI server (127.0.0.1, a port of the test's own, raw HTTP answers) or a simulated case: `inference.rs` (statuses, stream, transport, cancellation, `check`), `capture.rs` (capture and paste refusals), `error.rs` (the snake_case list), `lib.rs` (a result without target, the shortcut states).
- **A link to a field.** `open_settings({field?})` shows and focuses the settings window, then emits `settings-focus-field` `{field}` to it. Accepted: `menuShortcut`, `endpoint|apiKey|model` (the default profile's) and `quality.|fast.` + those; any other value only opens the window. The window is created hidden at startup: a link sent in the very first instant, before its page listens, only opens it.
- **The state of each shortcut.** `shortcut_status() -> ShortcutStatus[]`, one per binding in the settings order: `{bindingId, shortcut, state}` with `registered`, `taken` (Windows answered ERROR_HOTKEY_ALREADY_REGISTERED: another application holds the chord, the case of `Ctrl+Alt+Space` measured on 2026-09-24), `failed` (any other refusal) or `disabled`. Event `shortcut-status` (the same array) to the settings window once the startup registrations are done and after every save. A save tries the refused chords that are still wanted again (the other application may have let go) and never fails because of them; a new chord that is taken still refuses the save as before (« Le raccourci est déjà utilisé ou indisponible. »).

## Îlot: the lines of the selection (lot 5)

- **`Capture.selectionRects`** (absent when empty): the lines of a UI Automation selection, in **physical screen pixels** like `anchor` (the unit of `GetBoundingRectangles` under Per-Monitor V2), top to bottom then left to right. They are data for Rust's own placement: the frontend never positions anything from them. Whatever draws on them converts once, for its own window: `selection_lines::halo_frame(lines, scale, margin)` grows their union by `margin` logical pixels onto whole physical pixels (the window) and gives each line in logical pixels relative to that window's top-left corner, at the window's DPI scale (unit-tested at 100, 150 and 200 %, on screens at, right of and left of the origin).
- **From runs to lines** (`selection_lines::lines`): UIA gives one rectangle per visible run (several per line when the style changes, none for a line scrolled out of view). Runs that are not finite or have no area are dropped; the others are clipped to the source window (`GetWindowRect`) and dropped when nothing of them lies inside it. Runs overlapping vertically over half the shorter one form a line; within a line, runs merge unless a gap wider than the line height separates them (two table columns stay two segments). Beyond 64 segments: the first, the bounding box of those in between, and the last (three rectangles that never overlap).
- **Unchanged:** `anchor` stays the raw last rectangle UIA gives (none when that one is unusable), physical; the placement and `validate_target` compare it exactly as before. The synthetic copy, a copy the user made, a replay and an application without usable rectangles (VS Code's Monaco has no TextPattern) give no `selectionRects`: no effect on the text, the pill alone. `--demo-selection` carries two fixed lines ending on its anchor.

## Îlot: the halo window (lot 6)

- **Window.** `halo` (`/?window=halo`, created hidden at startup, `focusable: false`): transparent, no shadow, no material. `WS_EX_TRANSPARENT | WS_EX_LAYERED | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW` are set once at startup (with Tauri's `set_ignore_cursor_events(true)`) and re-applied at each placement; it publishes no surface, so the 8 ms hit tester never touches it and it never takes a click or the focus. Shown and hidden at the HWND (`host::place_below`, `host::hide`), never through Tao. It counts as one of our windows (a press over it never captures it) and receives `settings-changed` (theme, motion).
- **When.** Under `uiVersion: 'ilot'` only, when `translate` starts for a capture that still has its anchor and `selectionRects`: Rust places the window on the union of the lines + 12 logical px (`selection_lines::halo_frame`, at the DPI of the screen under the lines, placed again at the window's own DPI when Windows gives it another), right under the overlay (`SetWindowPos` inserted after `overlay`, `SWP_NOACTIVATE`), above the source, then emits `halo` `{generation, phase: 'work', lines, width, height}` (logical pixels relative to the window). It is placed once per run and never moved while it animates. Under v4, for the copy paths, a replay, or a capture whose selection was invalidated: no halo.
- **Until.** The response (`done` or `error` of the current request) sends `phase: 'leave'`: the page fades out in 150 ms and the window hides 200 ms later. It hides at once (`phase: 'clear'`) on a dismissal, a new capture, `cancel_translation` of the running request, and the context watcher's invalidation (source window moved or left, selection changed, scrolled or collapsed: `validate_target` compares the anchor, and a readable control that no longer holds a selection, after a click or an arrow key, counts as a change, so neither the halo nor a paste outlives it: before, such a paste inserted the result at the caret). While the halo is visible the watcher checks every 105 ms instead of 420 ms. A generation orders the calls: a stale leave or hide never touches a newer run, and the page ignores older generations.
- **Page** (`src/halo/`): one div per line, radius 3 px, the lab's `.tfx-sweep` (gradient 100° violet, pink, amber at .32, 1.6 s, `cubic-bezier(.4,0,.2,1)`) with its 300 % and 120 % → −20 % computed on the strip of all the lines laid end to end, so the band runs from the end of one line into the start of the next. It appears 250 ms after `work` (a JS timer, so it holds under reduced animations) with a 150 ms fade; under `data-motion="reduced"` a fixed veil in the same colours over the same strip. `html[data-halo-ready]` marks the listener as installed.
- **Marks (lot 9).** The same window draws the changed words of a replacement (`phase: 'marks'`, see « the result »): placed like the sweep on their lines + 12 px, the marks shown at once (260 ms in), held, 900 ms out at `leave`.
- **Test switch.** `FLOWTRANSLATE_SIMULATE_WORD_MS` (1 to 2000, simulated inference only): the delay between simulated words (65 ms by default), so the real-window checks can watch the halo while the work lasts.
- **Naming.** Unrelated to the shadow margin called `halo` in `src/layout.ts` and `glass.css` (the transparent room around the glass inside the overlay window).

## Îlot: window reserve, regions and pill (lot 7)

- **Reserve.** The Îlot's window is reserved once per menu capture for its largest shape, the field's width by the grid's height (283 × 116, `src/menu/metrics.ts`), plus the halo (`src/layout.ts`, `ilotReserve`); its shapes then only change the hit-test region, never the window, so no `SetWindowPos` ever runs while the surface springs (plan §4.3). **Anchored** (the capture has an anchor, whatever its length): 347 × 264, `presentation: 'anchored'`, `frame` = the compact strip `{x:32, y:104, width:283, height:32}` that Rust places like the glass footprint (8 px under the selection, or 8 px over it when the room below is short; its right edge on the selection's end, clamped into the work area). The Îlot hangs from the strip's right edge and grows away from the selection by at most 84 px; the reserve keeps that room on both sides of the strip (20 top halo + 84 + 32 + 84 + 44 bottom halo). **Bottom** (no anchor, clipboard): 347 × 152, `presentation: 'bottom'`, `frame` = the whole box `{x:32, y:20, width:283, height:116}`; Rust docks the window bottom-centre, the Îlot rests centred on the box's bottom edge (16 px above the window's) and grows up.
- **Side.** Rust chooses above or below at the first placement and keeps it for the capture. The frontend reads it back before the Îlot shows: once the first `resize_overlay` resolved, `getCurrentWindow().innerPosition()` (physical pixels, `core:window:allow-inner-position` of `core:default`) gives the window's top; the strip's top (`top + 104 × scale`) at or below the middle of the anchor means below (`ilotSide`). The entrance's transform origin is the corner facing the selection (right top below, right bottom above, centre bottom without anchor). If the position cannot be read within 400 ms, the Îlot opens below.
- **Regions.** One region, the Îlot's current shape, whole pixels, radius `height / 2` up to 44 px of height, else 16 (`ilotRegion`). A change of shape publishes, at its start, the box that holds both shapes (they share the corner or the bottom edge facing the selection) with the smaller radius, then, at its end, the new shape; identical geometries are not sent twice. Width, height, `frame` and `presentation` never change for the capture. The first geometry, sent before the Îlot has rendered, places and shows the window with a 283 × 32 region where the compact state will rest; the Îlot enters once that placement resolved (and, anchored, once the side is read), so its entrance plays in a visible window.
- **Pill.** After the choice the same surface (one DOM element, `[data-ilot-shape]`) springs to the working pill of lot 8: 44 × 28 (52 × 28 for the Ruban), radius 14, the indicator of `settings.indicator` after 250 ms, standing still under reduced motion and while the page is hidden (`WorkingContent`, `src/loaders/WorkingPill.tsx`). Same region contract; the pill sits in the strip's corner (anchored below: `{x:271, y:104, width:44, height:28, radius:14}`). A double press before the Îlot rendered makes it appear directly as the pill. The check, the automatic close 900 ms after `result-delivery: applied` and the fallback to the glass (`fallback`, error) are those of a direct « replace » capture; the glass then publishes its own reserve.
- Under `uiVersion: 'v4'` none of this applies; a direct capture under `ilot` keeps the standalone working pill in the glass reserve (`.working-pill`).

## Îlot: the result (lot 9)

- **After the paste.** Under `uiVersion: 'ilot'`, once the automatic paste succeeded, Rust finds the pasted text with UI Automation, still under the state lock (no capture commits in between): the range that ends at the caret (the end of the first selection range, so a paste that leaves its text selected works too) and spans the result's length in the provider's characters. Providers count UTF-16 units or code points and write a line break as CR, LF or CR LF: a few candidate lengths are tried and the one whose text reads back as the result (line endings and non-breaking spaces aside) is kept; three tries over about 200 ms. `result-delivery` `{status: 'applied'}` then carries `pastedRects` (the new text's lines, physical, grouped and clipped like `selectionRects`; absent when the text was not found) and `undoable` (found, and `afterReplace.undo` on). Under v4: no `pastedRects`, `undoable: false`. The texts (original, result, provider's copy) stay in Rust's memory for the comparisons: nothing emits, logs or stores them.
- **The pill's place.** `result_pill({requestId, width, height}) -> PillTarget` for a pill of that size (logical): its top-left corner relative to the overlay window as it stands, logical (negative, or beyond the window, when it does not fit there). `side: 'below'` (default): 8 px under the last line of the new text, its right edge on the end of that line, clamped into the work area; no room below: `above` the first line; `pillPlacement: 'margin'`: right of the widest line, level with the last one, tried first. Never over a line of the new text: `clear: false` only when no candidate fits the screen (then below, clamped). `estimated: true` when the pasted text was not found: the old selection's lines grown or shrunk by the ratio of the lengths, ending on the old anchor moved by that many lines. `inside: true`: the pill fits in the window there, the frontend moves its surface in the DOM (no `SetWindowPos`); `inside: false`: `move_overlay` first, then ask again. Refused for a stale request.
- **Moving the window.** `move_overlay({captureId, dx, dy})`: moves the anchored overlay window by (dx, dy) logical pixels and resolves once placed; the surfaces are relative to the window and move with it. Rust never moves the window by itself while the pill animates: the frontend calls it at a moment its surface rests (the check drawn, or the surface faded), then `result_pill` answers relative to the moved window. Every later placement of the capture keeps the shift (`resize_overlay`); a drag replaces it (the manual place), the next capture resets it. Refused for a bottom or unanchored form, a stale capture, a drag in progress, or a move larger than the work area.
- **Changed words.** `highlight_changes({requestId, ranges: TextRange[]}) -> HighlightResult`: `ranges` of the result in UTF-16 code units (JavaScript string offsets, `src/result/highlight.ts`), end excluded, at most 64 (« whole block » is one range from its first to its last visible character). Rust aligns them with the provider's text (CR LF against LF, non-breaking spaces), resolves each as a sub-range of the pasted text, checks its text, and draws its lines (a range's runs merge per line, two ranges never do; 256 lines at most) in the `halo` window, `phase: 'marks'`. Answers `{ranges, lines}`: how many ranges were found, how many lines are drawn (0: nothing shown, also when Undo is not offered or no longer is). The marks: `rgba(141,159,255,.32)`, radius 3 px, 260 ms in, held until `clear_highlight({requestId})` (the pill's countdown ended), a key in the source, Undo, a dismissal or the next capture; then 900 ms out, ease-out, the window hidden 950 ms after; under reduced animations, no animation.
- **Undo.** `undo_result({requestId}) -> UndoOutcome`, once per replacement. `undoStrategy: 'keystroke'` (default): Ctrl+Z to the source; `'repaste'`: the pasted text is selected (UIA `Select`), read back (Chromium applies the selection a moment later: up to 400 ms), and the original pasted over it through `capture::paste` (the clipboard kept as for any paste). Both: the source is brought back first when one of our windows holds the foreground (refused when another application does), then rule 1 after that reactivation: the same window, the same focused control, the same UIA element (runtime id), the pasted text still exactly right before the caret; the keys released (600 ms at most, else `keys_held`); all checked again. After Ctrl+Z, the original must read back (selected, or right before the caret) within 800 ms: `undone` with `confirmed: true`; a field that cannot be read: `undone`, `confirmed: false`; read and not back: `failed`, `paste_blocked`. `refused` means nothing was sent: `target_changed` (the text, the caret, the field or the window changed, or Undo was already withdrawn), `keys_held`, `paste_blocked` (the source cannot be brought back, the chord blocked before any key). The marks hide at once.
- **Undo withdrawn.** Event `undo-state` `{requestId, available: false, reason}` to the overlay, once: `typed`, a key went down in the source window (any key but the modifiers, the lock keys and Escape; another tool's injected keys count; our own keys carry `dwExtraInfo = 0x464C5754` and never do); `undo_key`, the user's own Ctrl+Z in the source (it passes through: the application undoes the paste itself); `caret_moved`, the watcher no longer finds the pasted text right before the caret (a click elsewhere, a selection, another field). The marks fade out. The frontend removes Undo; the pill stays until its time ends.
- **Watcher after the paste.** While a replacement is current the context watcher checks every 105 ms. The caret after the pasted text (the selection the paste collapsed) is normal and keeps pill and marks. The source window moving or resizing, another application in front, or the pasted text's rectangles moving by more than a pixel (a scroll, a reflow) dismiss: `overlay-dismiss-requested`, halo hidden. One of our windows in front (a click on the pill) changes nothing.
- **Tests.** Rust: the candidate lengths, the alignment, the provider's character index and an Undo refused without its source in front (`pasted.rs`), the pill's place and the estimate (`placement.rs`), the keys that end Undo (`host.rs`), the last line, a scrolled text and the shapes of the events (`lib.rs`). Playwright: the `marks` phase and its reduced form (`e2e/halo.pw.ts`). Real windows: Notepad and a Chrome `textarea` (reports of the lot, lengths and booleans only); Word and Outlook: manual recipe in docs/RECETTE.md.

## Commands

- `get_settings() -> Settings`
- `frontend_ready() -> Capture|null`: overlay-only handshake, called after event listeners register. Marks overlay ready and returns pending capture, if any. Frontend deduplicates capture IDs. Never recapture clipboard as a startup fallback.
- `save_settings({settings}) -> void` (validate URL/model/shortcut before saving; DPAPI-protect credentials)
- `capture_text() -> Capture` (also usable from preview/test controls). Since 0.4.0 `canReplace` is decided at capture (`capture::replaceable`): true for an editable UIA selection or a successful synthetic copy, false for the user's own fresh copy, a replay, a demo, a console window or a password field; no second step. Without a UIA selection Rust copies for the user (synthetic Ctrl+Insert after the shortcut chord is released, clipboard sequence watched ≤ 350 ms, previous text restored without feeding Win+V unless something else wrote in between), else accepts a copy the user made himself less than 3 s before (`host::track_clipboard`), else fails with « Rien à traduire dans la fenêtre active. » shown as a notice, never as a MessageBox.
- `translate({request:{id,captureId,text,mode,actionId}}) -> void`: starts background streaming and returns promptly. Emits `translation` StreamEvent. Register listeners before invoking. At most one active request; starting another cancels the prior one. Validate capture/text identity. Desktop demo may be explicitly started through CLI `--demo`, never silently substitute a mock for failed inference.
- `cancel_translation({requestId}) -> void`
- `copy_result({requestId}) -> void`: Rust copies only a completed known translation, never arbitrary frontend-supplied replacement text.
- `replace_result({requestId}) -> void`: menu « Remplacer »; revalidates the stored target, reactivates the source window and pastes once (`capture::paste`); the target is consumed even on refusal, the error string is shown as feedback.
- `dismiss_overlay() -> void`: cancel immediately and emit `overlay-dismiss-requested` with `{captureId}`. Native fallback hides after 300ms. When the overlay holds the foreground (Îlot menu), the source gets it back first.
- `choose_action({captureId,actionId,instruction?}) -> ExecutionInfo`: Îlot menu choice, once per menu capture (see the Îlot section).
- `shortcut_conflict({shortcut}) -> ShortcutConflict`: whether the chord is also AltGr + a key on the active layout (see the Îlot section, lot 4).
- `complete_overlay_dismiss({captureId}) -> void`: acknowledge the closing animation; stale acknowledgements do nothing.
- `open_settings({field?}) -> void`: shows the settings window; with `field` (a `SettingsField`, lot 13) Rust then emits `settings-focus-field` to it (lot 10).
- `shortcut_status() -> ShortcutStatus[]`: whether each binding's chord is registered, taken by another application, failed or disabled (lot 10).
- `result_pill({requestId,width,height}) -> PillTarget`: where the pill goes after a paste under the Îlot (lot 9, see « the result »).
- `move_overlay({captureId,dx,dy}) -> void`: moves the anchored overlay window by logical pixels, at a moment the frontend chooses (lot 9).
- `highlight_changes({requestId,ranges}) -> HighlightResult` and `clear_highlight({requestId}) -> void`: the changed words in the halo while Undo is offered (lot 9).
- `undo_result({requestId}) -> UndoOutcome`: Undo of the replacement, once, after revalidation (lot 9).
- `system_theme() -> {dark: boolean}|null` (lot 1): the Windows app mode (`HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize\AppsUseLightTheme`), for the setting « Theme: follow Windows »; null when the value is missing, and the front then keeps `prefers-color-scheme`. Event `system-theme` `{dark}` when the mode flips (`RegNotifyChangeKeyValue`). Needed because the app's WebView2 answers `prefers-color-scheme: light` whatever Windows says (measured on 2026-09-24: tauri-runtime-wry creates the WebView with an explicit light theme when tao does not detect dark mode).
- `system_motion() -> {reduced: boolean}|null` (lot 2 of docs/DA-PLAN.md): whether Windows asks to reduce animations (« Effets d'animation », `SPI_GETCLIENTAREAANIMATION`), for the setting « Animations : suivre Windows »; null when Windows does not answer, and the front then keeps `prefers-reduced-motion`. Read in Rust because nobody has measured whether WebView2 passes that switch on to the media query (it does not pass the app mode on to `prefers-color-scheme`, lot 1).
- `focus_overlay() -> boolean`: the Îlot menu's keyboard (see the Îlot section). Waits until the overlay is shown, brings it to the foreground (`SetForegroundWindow`), repairs the frameless style and answers whether the overlay really holds the foreground afterwards. Overlay and halo visibility never goes through Tao's `show()`/`hide()`: Tao 0.35 rebuilds the styles with `WS_CAPTION` on its deferred visibility diff, which DWM paints as a title.
- `start_drag({clientX,clientY}) -> void`: only overlay; starts native movement after a primary pointer press on non-interactive content. Coordinates are logical client pixels captured on pointerdown; Rust validates them and compensates pointer travel before IPC delivery, then uses native dragging while the button remains pressed. Retain the manual location across streaming/menu resizes until the next capture. Buttons and scrollbars keep their own interactions.
- `resize_overlay({width,height,captureId?,presentation?,regions?,frame?}) -> void`: logical pixels. Since 2026-09-14 the ceiling is the work area of the screen the window rests on (physical against logical, no more 640×800): a larger window is refused with « Dimensions invalides. ». The bounds include the shadow halo (32 px each side, 20 px above, 44 px below anchored, 16 px below the bottom band) and are **reserved** once per capture (`src/layout.ts`): anchored, 444 × max(measured glass, 334) so the wait pill, the short glass and the menu under its pill only change the regions; bottom, `bottomReserve(screen, preset)` (band width + 64, by top halo + 236 px menu reserve above the pill + pill band + tallest band + 16) with the root projected on the window's bottom edge. `frame` is the glass footprint Rust anchors and clamps into the work area: while waiting, the 380 × one-line footprint of the glass to come, so the pill alone already sits where the glass opens; afterwards region zero. Regions are unchanged (one to six tight rounded surfaces, hit-test only: the window carries no Win32 region, Chromium paints the silhouette with per-pixel alpha and `host::start_hit_tester` polls the cursor every 8 ms to toggle `WS_EX_TRANSPARENT | WS_EX_LAYERED`). Rust applies the rectangle (`host::place`) only when it changed and the surfaces (`host::set_regions`) whenever they changed: a regions-only update costs no `SetWindowPos`. A work area shorter than the reserve truncates the bottom window from the top and Rust shifts the regions accordingly; anchored, only the glass is clamped, the transparent reserve may leave the work area. Stale capture IDs do nothing.
- `presentation: 'anchored' | 'bottom'` (2026-09-14, replaces contextual/reader/docked): the form is decided once, on the settled result, and never switches afterwards (no « Agrandir », no tab, no fold). `anchored`: the short glass (≤ 8 lines at 380 px) opens from its wait pill beside the selection, keeps its chosen side and its drag position. `bottom`: the reader band (half the work area wide, at most 45 % of its height, whole lines, scrollable beyond) rests bottom-centre of the **cursor's** screen (`host::monitor_at(None)` at the switch, `manual` reset), bottom edge anchored, and follows the cursor across screens (see `work-area`). Clipboard and unanchored captures open bottom.
- `overlay_dimming({dimming}) -> void`: the reading budget is spent and the frontend starts the two-step exit (55 % in 600 ms, held 1.4 s, 300 ms fade) → Rust closes the Escape scope so Escape belongs to the user again; `dimming: false` (an approach, a wheel or a key restored the glass for 5 s) re-arms it while the window is visible. Then `dismiss_overlay` / `complete_overlay_dismiss` as before. Budget (`src/layout.ts`, `readingBudget`): orientation (1 s anchored, 1.5 s band) + 350 ms per word, between 5 s and 30 s (short) or 90 s (band), scaled by `autoClose`; a pointer visit of at least one second followed by a departure shortens what remains to 4 s, never below 2.5 s; a click, wheel or key restores the whole budget; the pill's pin (band only) suspends it.
- `drag_settings() -> void`: settings window only; starts the native move from the home-made title bar.
- `quit_app() -> void`: exits the application (settings footer).
- `check_connection({mode}) -> ConnectionStatus` (with `code` when not connected, lot 10)
- `get_history() -> HistoryEntry[]`
- `delete_history({id: string|null}) -> void`: null deletes all.

## Events and windows

- `halo` carries `HaloEvent` to the halo window only (lot 6, see above); older generations are ignored.
- `menu-repeat` carries `MenuRepeat` to the overlay: the double press of the menu shortcut (lot 4); `useTranslation` runs the last action of that application; stale capture ids are ignored.
- `menu-key` carries `MenuKey` to the overlay: a menu key the native hook took from the source while the Îlot menu waits and the overlay never held the foreground for it, or while its capture was still being taken (held, then emitted after `capture`); stale capture ids are ignored.
- `capture-target` carries `{captureId, canReplace}`: since 0.4.0 only `canReplace: false`, once a paste consumed the target (automatic or from the menu); a stale capture id is ignored.
- `result-delivery` carries `ResultDelivery` after the automatic paste of a « replace » capture (see above); under the Îlot, `pastedRects` and `undoable` (lot 9).
- `capture-notice` carries `{message}`: nothing to translate, protected field, oversized selection, source window changed. Without an open glass Rust first places the overlay window as a pill alone (420×64 logical, bottom centre of the cursor's screen, no surface: the mouse passes through) and hides it after 4 s; with an open glass the frontend shows the message as feedback. Replaces the MessageBox (2026-09-14).
- A `capture` with `replay` (tray « Revoir la dernière traduction », kept 10 min after the glass closed) is shown complete by the frontend without invoking `translate`; `copy_result` accepts its request id.
- `work-area` carries `Screen` (logical work area and scale) to the overlay when the cursor moved to another screen while a bottom form is visible: the hit tester reports `MonitorFromPoint(cursor)` on change, `screen_changed` moves the window to the new screen (`placement::docked` on its work area) and the frontend recomputes the band width and republishes its geometry. An anchored glass belongs to its selection and never follows. `capture.screen` carries the same values for the first computation. No cursor position is emitted.
- `capture` carries Capture to overlay, after it is ready; every capture starts translation at once in React (the clipboard confirmation step was removed on 2026-09-10). The global shortcut always captures the current selection, clipboard fallback included; it no longer focuses an existing glass.
- `translation` carries StreamEvent. React ignores stale request IDs. Rust emits done only on normal, non-truncated completion.
- `settings-changed` carries Settings after successful persistence.
- `settings-focus-field` carries `SettingsFocus` to the settings window: scroll to that field, focus it, highlight it (lot 13; sent by `open_settings({field})` since lot 10).
- `shortcut-status` carries `ShortcutStatus[]` to the settings window after the startup registrations and after every save (lot 10).
- `undo-state` carries `UndoState` to the overlay when Undo is no longer safe: a key in the source, the user's own Ctrl+Z, the pasted text no longer before the caret (lot 9).
- `system-motion` carries `{reduced: boolean}` to every window when « Effets d'animation » flips: a hidden top-level window of the `system-motion` thread re-reads `SPI_GETCLIENTAREAANIMATION` on each `WM_SETTINGCHANGE` and emits only a change.
- `target-invalidated` carries `{captureId:string,anchorLost:boolean,message:string,code:'target_changed'}` (code since lot 10): ignore stale capture IDs; disable replacement and native window moves to bottom only when anchorLost. Never sent for a menu still waiting for its choice: that menu closes instead (see « Leaving the menu »).
- `overlay-dismiss-requested` carries `{captureId:string}`. Frontend completes its exit animation then acknowledges it; a new capture invalidates the old request and timeout.
- `glass-near` carries `{near:boolean}` to the overlay, emitted by the hit tester on change only: whether the real cursor rests within 32 logical px of one of the published regions (the silhouette and its shadow, never the whole reserved window). The frontend holds the glass open while `near` is true and starts its 500 ms fold once it turns false; a click grants two seconds regardless. No cursor position is ever logged or emitted.
- Window labels: `overlay` loads `/?window=overlay`, `halo` loads `/?window=halo`, `settings` loads `/?window=settings`.
- Only overlay subscribes to capture/translation and starts requests. Settings and halo may subscribe to settings-changed (the halo also to `halo`), never trigger translation from global capture events.
- The capsule window, no longer shown since 2026-09-10, was removed with lot 6 (docs/DA-PLAN.md §4.2): its entry in `tauri.conf.json` and the capabilities, its Rust placement and Escape scope, the `Capsule` component, its styles, messages and lab scenario. Its tests were rewritten for the halo; `focus_overlay` stays (the Îlot menu).
- Frontend publishes no IPC command capable of executing a shell, opening arbitrary files, or injecting arbitrary keystrokes.
- Showing/resizing never activates the overlay; only `focus_overlay` does, for the Îlot menu, and after a choice the overlay cannot be activated at all until the next capture. Escape is captured by a scoped native hook only while overlay is open if the source retains focus; while the Îlot menu is open the hook takes only the menu keys, and only when the source kept the foreground because the overlay never got it. No unrelated keys are intercepted, and no key is ever logged.
- Glass calibration since 2026-09-14: one graphite `rgba(24,26,31,.96)` for glass, pill and menu, a 1 px 20 % edge, no sheen; copy `#e8eaef`, letter-spacing 0, `text-wrap: pretty`, sizes from the `textSize` preset (`--copy-size`/`--copy-line`). The packaged window paints **no native material**: `DWMWA_SYSTEMBACKDROP_TYPE` (Tauri `Effect::Acrylic`) is drawn behind the entire window bounds regardless of the window region (the grey frame Lucas reported) and any material shows through DOM fades. `FLOWTRANSLATE_GLASS=blur|acrylic|dwm` re-enables a material for experiments (`host::apply_glass`). The browser preview keeps its own `backdrop-filter`. Text stays fully opaque. Shadows live in the halo (`--glass-shadow: 0 12px 32px rgba(0,0,0,.34)`, glass.css sizes the halo to it); the halo never blocks a click since the hit-test reads the tight regions.
- Rust preserves the chosen above/below side during a stream; the deltas are buffered in `useTranslation` (2026-09-10) and, since 2026-09-14, the wait is a pill alone (60×28, shadcn's spinner: lucide `LoaderCircle` 18 px turning once a second, a sweep after 1.5 s) at the upper-right of the glass to come; the settled text is measured off-screen at 380 px (`measureLines`) and the form is decided once: ≤ 8 lines → short glass unfolded from the pill (`clip-path`), more → reader band. Since 0.2.1 (UI-025) the placement itself is decided at the capture on the source text (`decidePlacement`: anchored and ≤ 8 lines → beside the selection, else bottom), so a long selection waits at the bottom from the start and the band is born there; only a short source translated long still moves to the bottom invisibly before the band rises 8 px in 220 ms. When the switch to `bottom` lands on another screen than the selection's, Rust emits `work-area` at once. `start_drag` is only invoked after 4 px of pointer travel; Rust still compensates the travel since the press. When geometry is genuinely lost, re-anchor to bottom explicitly.
